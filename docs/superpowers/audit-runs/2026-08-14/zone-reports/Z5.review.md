## 三、严重度异议

### S1 — F507：P2 → **P1**（审计完整性缺陷，数据丢失路径静默放行）

理由：按严重度决策表，P1 触发条件含"正常路径可复现功能错误"，P0 含"数据损坏/丢失"。F507 描述的行为（技能删除自身声明写入的 truth 文件，写审计零拦截、GATE 静默 PASS）是**数据丢失路径上的门禁静默放行**——审计（支柱四 Tier B）的存在目的即拦截写越权，删除是最强写越权。当前 OWNERSHIP 参考条目含 truth/pending_hooks.md（5 个技能条目），一旦任一技能删除该文件，`status="deleted"` 下所有 detail 字段为空 → 全 level 无违规 → ship 放行。虽然删除需技能异常行为触发（故不升至 P0），但审计对自身覆盖的 status 词表（deleted）完全无拦截逻辑，属正常路径可复现的审计功能错误，P2（边界/错误处理）低估。建议升 P1：在 check_write_ownership 增加 deleted 分支（OWNERSHIP 文件删除即违规；非 OWNERSHIP 已声明文件删除至少告警），并补删除场景测试。

### S2 — F512：P2 → **P1**（支柱四写审计在正常 pipeline 路径零执行）

理由：决策表 P1 触发条件含"违反 AGENTS.md 显式契约；正常路径可复现功能错误"。AGENTS.md/支柱四 spec 将写所有权审计定位为 Tier B 门禁；而 dispatch_skill 的 API 路径（`SHENBI_LLM_API_KEY` 设置时即主路径）与 IDE 路径**完全不执行写审计**，仅 fallback 的 legacy CLI 路径执行——且该路径快照根还错位（F513）。即主 pipeline 的正常执行路径（API 优先）下，写越权审计**恒不运行**，属"正常路径可复现的功能缺失"。初审自述"若支柱四 spec 要求 pipeline 覆盖则需升 P1"——spec 支柱四明示写所有权审计为 pipeline 级（spec 4/5 档），故升 P1。建议：在 `_dispatch_via_api`/`_dispatch_via_ide` 接线 write-audit（复用 F513 修复后的快照语义），或显式降级为文档声明的"仅 legacy 路径"并更新 dispatch_helper docstring。
