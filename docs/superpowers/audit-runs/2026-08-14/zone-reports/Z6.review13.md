## 2. 新发现（F661-F662）

### F661 | `_short_chain_chars` 正则无左锚：长句尾部可充当"短句"入链、被长句打断的短句链整体丢失 → short_sentence_chain_density 在真实章节上系统性偏差（ch46 上正则 0 vs 正确语义 57） | 统计口径（F633/F656 同族） | P2（潜伏）

- 证据：`src/shenbi/skill_utils/drift_detection/linguistic_drift.py:88-91`（`_short_chain_chars`：`re.findall(r"(?:[^。！？\n]{1,15}[。！？\n]){3,}", text)`）；docstring :89（"Count characters in chains of 3+ consecutive short sentences (<=15 chars)"）；消费方 `compute_linguistic_metrics` :114（`short_sentence_chain_density = _short_chain_chars(text) / text_len * 1000`）——经 `_check_linguistic_drift`/`establish_baseline` 进入漂移检测链（当前因 F602 无 baseline 潜伏）。
- 根因：正则 `(?:...){3,}` 的每个 group `[^。！？\n]{1,15}[。！？\n]` **无左锚**（不要求从句子开头开始），且 findall 只返回非重叠匹配：
  1. **长句尾部入链（高估）**：任一以句末符结尾的 ≤15 字符片段（含长句最后 ≤15 字）都可充当一个 group——26 字长句 + 3 个短句的文本，匹配结果为 `'很长很长的句子因为要超过十五字。短句一。短句二。短句三。'`（长句尾部 15 字被计为"短句"），本轮实测 count=28（仅短句应为 ~13）；
  2. **打断丢失（低估）**：3+ 短句链中间夹一个 >15 字长句时，正则无法跨过长句继续匹配 → 长句之前的短句整段不计；且 findall 的贪心匹配可能跳过链首。
  - 两方向净效应随文本组成而变：真实章节 1/2/45/46 实测 **regex vs 按"连续 ≤15 字句子 run"锚定语义的计数 = 196 vs 306（Δ-26.3‰）、0 vs 0、44 vs 69（Δ-2.1‰）、0 vs 57（Δ-4.3‰）**——ch46 正则完全漏检一章真实存在的短句链。
- 验证命令+输出：
  ```
  PYTHONPATH=src python3 -c "
  from shenbi.skill_utils.drift_detection.linguistic_drift import _short_chain_chars
  _short_chain_chars('这是一个超过十五个字符的很长很长的句子因为要超过十五字。短句一。短句二。短句三。')
  -> 28   # 长句尾部 15 字 + 3 个短句全部入链（应只计短句 ~13）
  ch1: regex=196 anchored=306（Δ-26.3‰）；ch46: regex=0 anchored=57（Δ-4.3‰，正则完全漏检）
  "
  ```
- 影响：short_sentence_chain_density 不是文档承诺的"连续 ≤15 字短句链字符数"，绝对值系统性失真（-26‰~+15 字级）；漂移检测用相对比值（current/base），若 baseline 与 current 文本组成不同（如对话变多/变少）比值会失真。当前 F602 无 baseline → 潜伏；接线后即带病测量（与 F601/F605/F612/F634/F636 同属"接线即激活的测量缺陷"族）。测试 test_linguistic_drift.py 只测单值不锁量级 → 未发现。
- 建议方向：改为先按句末符切句、再找连续 ≥3 个 ≤15 字句子的 run 并求和（`re.findall(r"[^。！？\n]{1,}[。！？\n]", text)` + run 扫描），或在正则 group 前加左锚（`(?:^|[。！？\n])([^。！？\n]{1,15}[。！？\n]){3,}`）并核对语义；补单测（长句+短句链只计短句；短句链中间夹长句时两侧均正确计入）。

### F662 | materialize `_as_float` 对 str 分数静默置 0.0（同模块 `_as_int` 却接受 str）——MARK_DONE score 为字符串时分数被静默抹零 | 边界/错误处理（F640 同族、潜伏） | P2（潜伏）

- 证据：`src/shenbi/trace/materialize.py:18-23`（`_as_int(value, default)`：`isinstance(value, (int, float, str))` 时 `int(value)`；`_as_float(value, default)`：**仅** `isinstance(value, (int, float))` 时 `float(value)`，否则返回 default）；`:60`（`"score": _as_float(payload.get("score"), 0.0)`）。
- 根因：同一模块内两个数值转换辅助函数对 str 的处理**不对称**——`_as_int` 接受 str（`"88"` → 88，非数值 str 则 ValueError 崩溃，review11 维持观察已述），`_as_float` 对 str **静默返回 default 0.0**。若未来任何生产者（F640 修复接线方向）以字符串写入 MARK_DONE 的 score（JSON 中 score 以 str 序列化是常见形态），materialize 重建的 progress 会把该分数静默记为 0.0——分数数据丢失且无任何日志/告警（与 `_as_int` 的崩溃行为形成"一个崩溃、一个静默吞"的反向不对称）。
- 验证命令+输出：
  ```
  PYTHONPATH=src python3 -c "
  from shenbi.trace.materialize import _as_int, _as_float
  print(_as_int('88', 0), _as_float('88', 0.0), _as_float(88, 0.0))
  -> 88 0.0 88.0    # str 分数：_as_int 转 88，_as_float 静默 0.0
  "
  ```
- 影响：F640 已确立该路径零生产者（INIT/MARK_DONE 全仓仅 materialize.py 消费）→ 当前潜伏；但 F640 的修复方向 (a)（接线真实写者）一旦实施，str 分数即静默抹零——与 F640 修复绑定评估，是"修复接线即激活"的潜伏缺陷（与 F640 同族，独立失败模式：类型处理不对称而非无生产者）。
- 建议方向：`_as_float` 与 `_as_int` 对齐——接受 str 并 `float(value)`（非数值 str 抛 ValueError 与 `_as_int` 一致，或统一 try/except 回退 default + WARN）；补单测（MARK_DONE score="88" → materialize 分数 88 而非 0.0）。
