### 1.3 P0 理由（对照决策表）

- **数据损坏/丢失**：staging/ 中待人审的 chapter-planning / state-settling 产物（spec §2.7 的 checkpoint-gated 中间产物）在每次正常进程退出时被 rmtree 整体删除；人审 approve 的提交路径随后静默 no-op → 产物确定性丢失。
- **契约被静默违反导致错误执行**：approve 决策下管线以"无 plan/truth 状态"继续推进（drafting 走 minimal context fallback，chapter_loop.py:1162-1197），人审通过 = 无效；MODIFY 决策下 chapter-planning 无限循环（每轮重发 plan → 退出清空 → 再 MODIFY）。
- **状态污染**：持久化 current_step 被无差别改写为 `EMERGENCY_SHUTDOWN_AT_*`（含正常完成态），resume heal（cli.py:706-718）虽能修但 `pipeline status` 与所有直接读 state 的消费者看到错误状态。

## 三、新发现（F3B6-F3B7）

### F3B6 | `register_emergency_handlers` 每章重复注册 atexit 钩子 + `reset_emergency_state` 注释声称移除钩子但从未 unregister → 钩子累积、退出时 N 次清理、current_step 嵌套污染 | error | **P2**

- **证据 file:line**：
  - chapter_loop.py:2508-2510：`if step_idx == 0: register_emergency_handlers(...)` —— 每章开始（`_complete_chapter` chapter_loop.py:923 重置 `step_index = 0`）都满足 step_idx==0 → 每章重复注册。
  - crash_recovery.py:64-66：`signal.signal(...)` ×2 + `atexit.register(_emergency_cleanup)` —— 无去重。
  - crash_recovery.py:39-42：`reset_emergency_state` 注释 "and remove any atexit hooks registered by earlier tests" 但只 `signal.signal(SIG_DFL)` ×2，**无 atexit.unregister**。
  - crash_recovery.py:113-117：`_emergency_cleanup` 每次执行都把 current_step 改写成 `EMERGENCY_SHUTDOWN_AT_{current_step}` —— 第 2 次执行时 current_step 已是 `EMERGENCY_SHUTDOWN_AT_...` → 嵌套。
- **根因**：注册点未做"只注册一次"保护；`reset_emergency_state` 的注释承诺与实际实现漂移（测试隔离契约未兑现）。
- **验证命令 + 输出**（/tmp 沙箱，真实进程语义）：
  ```bash
  # z3test4/double_register2.py: register 两次 + 正常退出
  persisted current_step: 'EMERGENCY_SHUTDOWN_AT_EMERGENCY_SHUTDOWN_AT_chapter_complete'
  # z3test5/reset_test.py: register 两次后 reset
  atexit handlers after 2 registers: 3
  atexit handlers after reset (claim: removed): 3   # 钩子未被移除，注释漂移实证
  ```
- **影响**：50 章 pipeline 退出时 `_emergency_cleanup` 执行 50 次（每次 save_state + rmtree + 快照覆盖，幂等但显著 I/O 浪费与日志噪音）；current_step 嵌套污染使 `pipeline status` 输出 `EMERGENCY_SHUTDOWN_AT_EMERGENCY_SHUTDOWN_AT_...`；`reset_emergency_state` 的测试隔离契约（docstring 明示）被违反，xdist 下跨测试钩子残留。严重度 P2（放大面 + 契约漂移；非独立数据损坏源——嵌套值仍被 resume heal `startswith("EMERGENCY_SHUTDOWN")` 前缀匹配覆盖）。
- **建议方向**：注册前 `atexit.unregister(_emergency_cleanup)` 或模块级 `_registered` flag 保证单次注册；`reset_emergency_state` 补 `atexit.unregister(_emergency_cleanup)`（兑现注释承诺）；`_emergency_cleanup` 在改写 current_step 前先剥离已有 `EMERGENCY_SHUTDOWN_AT_` 前缀。

### F3B7 | atexit `_emergency_cleanup` 在 WriteLock 释放后无锁写 pipeline-state.json + clear_staging → 与并发 `pipeline next/review` 的锁保护写形成竞态 | error | **P2**

- **证据 file:line**：
  - cli.py:598-618（cmd_next）/ :689-790（cmd_resume）：`with WriteLock(project_dir): ... save_state(...)` —— 锁内写；块退出后进程才返回 main → atexit。
  - crash_recovery.py:122-126 / :143-148：`_emergency_cleanup` 在 atexit 阶段调用 `save_state` + `clear_staging`，**全程无 WriteLock**（crash_recovery 不持有、cli 的 with 块已退出）。
  - cli.py:458-459（cmd_init）/ :511-568（cmd_review）同样 `with WriteLock` 写 state —— atexit 无锁写与这些锁保护写无互斥。
- **根因**：紧急清理被设计为"任何退出路径兜底"，但 atexit 阶段脱离命令的锁上下文执行持久化写；项目文件锁（filelock_utils）只保护命令内操作，不保护解释器退出钩子。
- **验证命令 + 输出**：代码路径静态确认（grep `with WriteLock` cli.py:458/511/599/689 + crash_recovery.py 无任何 flock/WriteLock 引用）；并发实测需双进程时间窗，属竞态缺陷按代码路径判定。已在 /tmp 验证 atexit 确实在锁释放后执行（实验 A：register 后正常退出，save_state 落盘篡改值——此时 cmd 的 with 块早已退出）。
- **影响**：两个并发进程（如 A 持锁运行 `pipeline next` 长任务、B 恰好在本进程退出触发 atexit 无锁写）对 pipeline-state.json 无互斥写 → state 版本不确定（篡改值 vs 合法值互相覆盖）；clear_staging 同样可并发 rmtree。触发需进程退出与另一进程持锁写的时间窗重叠，属并发竞态（决策表 P1 触发条件"并发竞态"的下限情形，但因其复用 F364 已 P0 的根因路径、且实践中 CLI 为串行调用为主，裁 P2 放大面）。
- **建议方向**：`_emergency_cleanup` 内 save_state/clear_staging 包裹 WriteLock（或与 F364 一起改为"仅紧急 flag 置位才清理"并移除 atexit 无条件注册——根治方案）；或至少用文件级原子写（safe_write 已原子）+ 文档声明 atexit 阶段不保证与命令锁互斥。
