## 一、过滤实现分析（fields.py vs 契约）

### 1.1 实现本体（`src/shenbi/contracts/fields.py`）

| 契约声明（AGENTS.md:82-89 + spec archive） | 实现 | 实测 |
|---|---|---|

| 声明字段缺失 → 返回全文 + WARN（escape hatch） | 零命中 → `log.warning("field_filter_no_match", ...)` + 返回原文 | **只对"全部缺失"成立**（`if not matched:` :61-63）；部分命中 → matched=True、无 WARN、未命中 section 静默丢弃（F218）；**触发路径在 pipeline 不可达**（T301） |
| canonical rule（strip + 折叠 U+3000/ASCII 空白 + 去零宽 + NFKC，不 lowercase） | `_normalize_ws`（:19-31） | md 路径经 `match_field` 一致；**json 路径裸 `k in fields`（:76）不规范化**（F230，复核轮已证伪"md/json 同构"） |
| `extract_h2_sections` 无围栏/重复标题处理 | :38-52 逐行 `startswith("## ")` | 代码围栏内伪 H2 干扰 + 重复标题后者覆盖前者（F264 已覆盖围栏；F264 review14 重复标题实例） |
| 非 md/json 扩展名 | :91 `return text, True` | **静默跳过**：不过滤、matched=True、无 WARN（T305，latent） |

### 1.2 消费链路（全量 grep 结果）

`filter_to_fields` 的生产引用**唯一**：

```
src/shenbi/pipeline/dispatch_helper.py:38   import
src/shenbi/pipeline/dispatch_helper.py:592  content, _matched = filter_to_fields(content, fields, str(full_path))
```

- **pipeline API 路径**（`_dispatch_via_api` → `_build_skill_prompt` :1506）与 **IDE 路径**（`_dispatch_via_ide` → `_build_skill_prompt` :1710）共用 `_build_skill_prompt`。
- **legacy CLI 路径**（`shenbi-dispatch` → `executor.dispatch` → codex 子代理）完全不构建 prompt：codex 以 `-C round_dir` 直读文件，无任何过滤（F225 已有；executor.py:99-103 `derive_input_files` 只用 `load_contract(skill)["reads"]` 纯路径）。
- `read_fields` 的唯一生产消费点是 `dispatch_helper.py:1229` `_collect_declared_truth_fields` → 仅用于 genesis truth 模板播种（:1238-1257）。**没有任何代码路径把 `read_fields` 喂给 `filter_to_fields`。**

### 1.3 ★ T301 根因（死代码）：`_build_skill_prompt` 的 dict-form 分支永远为假

`legacy.load_contract`（:165-197）把 dict-form reads **拍平**：`validated["reads"] = paths`（纯字符串 list），字段单独存入 `read_fields` dict。而 `_build_skill_prompt`（dispatch_helper.py:570-578）在拍平后的 `reads` 上检查 `isinstance(read_path_entry, dict)` —— **永远为 False**，于是 `fields` 恒为 `[]`，:591 `if fields:` 恒不成立，:592 的 `filter_to_fields` **从不带非空 fields 被调用**。

运行时 probe（`load_contract('shenbi-chapter-planning')`）证实：`reads` 7 项全为 `str`，`fields` 全为 `[]`；`read_fields` 中 3 组字段（主角状态/当前世界局势/活跃线索 等）从未被该循环读取。

**结论**：AGENTS.md:84-86 声称的"The dispatcher filters file content to only declared fields before the LLM sees it"在 pipeline 三条路径中**均未发生**；escape hatch WARN（`field_filter_no_match`）的唯一触发入口不可达，**生产中永不出现**。14 个 skill 的 dict-form 声明、13 个文件的字段过滤、genesis 播种的字段模板，全部是"声明存在、执行缺位"。

### 1.4 escape hatch 真实日志路径

- WARN 由 `fields.py:62/78` 的模块级 `structlog.get_logger()` 发出；`logging.py` 配置输出到 **stderr**（`PrintLoggerFactory(file=sys.stderr)`，`SHENBI_LOG_FORMAT=json` 时 JSON lines）。
- 直接调用可复现（本轮实测）：全缺 → `[warning] field_filter_no_match available=[...] fields=[...]` 打到 stderr，`matched=False`、全文返回。
- **但 pipeline 中不可达**（T301）：唯一调用点传空 fields；且 :592 `_matched` 被弃用（F218 已注），即使过滤运行，调用方自身也不记录任何日志。
- 附带：G1 的字段漂移 WARN 机制（`check_fields_exist`）同样是死代码（T304），因此"skill 作者在过滤前看到漂移警告"（g1.py:107 注释）也从未发生。

## 三、findings（T3xx）

### T301 · [P1] pipeline 字段级过滤为死代码：`_build_skill_prompt` 的 dict-form reads 分支永远不触发，`filter_to_fields` 唯一生产调用点恒传空 fields

- **证据**：`legacy.load_contract`（:165-197）把 dict-form reads 拍平为 `reads`（list[str]），字段单独存 `read_fields`；`dispatch_helper.py:570-578` 在 `contract["reads"]` 上做 `isinstance(read_path_entry, dict)`（:572）——恒 False，`fields` 恒 `[]`，:591 `if fields:` 恒不成立。运行时 probe 证实（`load_contract('shenbi-chapter-planning')` → 7 项 reads 全 str、fields 全 []）。grep 全 src：`filter_to_fields` 生产引用仅 :592 一处，`read_fields` 生产消费仅 :1229（模板播种）。
- **影响**：AGENTS.md:84-86 显式契约（"The dispatcher filters file content to only declared fields before the LLM sees it"）在 API/IDE/legacy-CLI 三条路径**均未实现**；13 文件 × 14 skill 的 dict-form 声明全部空转；escape hatch WARN 生产不可达；:592 `_matched` 弃用。同时**证伪 F218 的生产影响面**：部分匹配静默丢 section 仅在直接调用 fields.py 时可复现，pipeline 中过滤根本没跑（全文恒透传）——F218 的 P1 实害目前是 latent；若按契约修复本 finding，F218 立即在生产路径激活。
- **测试掩盖**：`tests/unit/contracts/test_fields.py`、`tests/unit/pipeline/test_field_filtering.py` 只测 `fields.py` 函数本体，无任何测试断言 `_build_skill_prompt` 输出含过滤内容 → 接线断裂无覆盖。
- **建议**：`_build_skill_prompt` 改用 `contract["read_fields"][path]` 取 fields（与 `_collect_declared_truth_fields` 同源），删死分支；补"断言 user_prompt 不含未声明 section"的接线测试。

### T302 · [P1] `lint_contract_fields` 假阴性：基准 fixtures 与声明自洽，真实 run/生产者模板漂移全部漏检（exit 0）

- **证据**：lint 实测 `exit=0`；其样本解析（`resolve_sample`）落到 2026-06-12/06-11 旧代 fixtures（style-profile-example.md 旧 11 节编号、snapshots/chapter-025 truth 含 主角状态/活跃伏笔/已完成章节），与声明一致；`outline/volume_map.md` 显式 `None` 跳过。真实 run（`novel-output/xinghuo-ranqiong`，2026-07-17）9 个漂移文件（见对照表）与当前生产者模板（style-learning `5. 修辞模式`/`8. 综合画像`、volume-consolidation 逐卷 H2、memory-distill L4 `未解决的张力悬置（带入下一大弧）`）全部未进入 lint 基准。
- **影响**：F262 声明的系统性漂移在 CI 上零信号；"Any drift the lint flags would also be a runtime WARN/FAIL"（lint docstring）为假——运行时若启用过滤（T301 修复后）将触发 escape hatch/部分匹配，而 CI 全绿。测试掩盖（决策表 P1"测试掩盖"）。
- **建议**：lint 基准改为真实 run 快照 + 生产者模板抽取（从 producer skill 输出格式节提取 H2），fixtures 仅作补充；volume_map 补样本或显式 FAIL。

### T303 · [P2] 4 个 group skill 正文手写 `## Contract` 块与 frontmatter 双源漂移（含字段声明永不生效）

- **证据**：`shenbi-review-group-{character,craft,factual,plan}/SKILL.md` 在 AUTO-GENERATED 区之后有手写 `## Contract` YAML 块（group-factual :46-55 等），含 dict-form fields（group-character `genre-config.json: [povMode]`、group-factual 3 处 fields）；与 frontmatter 不一致（group-factual body `writes: []` vs frontmatter 3 个审计写入；frontmatter 全部 string-form reads）。`load_contract` 只读 frontmatter，正文块零消费；grep 无任何工具生成该块。
- **影响**：文档展示的"字段级过滤已声明"在 4 个 skill 上是假象；review2 对 review-group-character"read_fields 声明永不命中 → :592 escape hatch 每次全文"的推断前提（字段在 frontmatter）不成立——字段根本未进 read_fields。与 F262 互补：F262 是声明 vs 生产者漂移，本 finding 是同一文件内 frontmatter vs 正文双源漂移。
- **建议**：删除正文 `## Contract` 块或改为 AUTO-GENERATED；若需保留，加 lint 校验正文块与 frontmatter 一致。

### T304 · [P2] `check_fields_exist`（G1 字段漂移 WARN）为死代码：无生产调用，D21 播种机制为其服务的假设不成立

- **证据**：grep 全 src，`check_fields_exist` 定义于 `gates/g1.py:102-144`，**无任何调用**（`gate_G1` :147-291 只跑 G1.1-G1.6；gates/cli.py:88 传参无 fields_map）。测试 `tests/unit/gates/test_g1_fields.py` 与 `tests/unit/pipeline/test_dispatch_helper.py:344 test_template_satisfies_check_fields_exist` 专测该死函数 → 测试掩盖。dispatch_helper.py:1201 注释声称播种模板"避免触发 G1 check_fields_exist"——该门从未存在。另：其匹配为裸集合差（:132 `set(fields) - actual`），即使接线也与 `match_field` canonical rule 不一致（全角空格/U+3000 会误报）。
- **建议**：在 `gate_G1` 中接线（用 `read_fields` 构建 fields_map，匹配改用 `match_field`），或删除死函数与对应测试并修正注释。

### T305 · [P2] `filter_to_fields` 对非 md/json 扩展名静默跳过：不过滤、matched=True、无 WARN（latent）

- **证据**：`fields.py:87-91` 仅 `.md`/`.json` 分支，其余 `return text, True`。运行时 probe：`filter_to_fields('anything', ['field'], 'file.yaml')` → 原样返回、matched=True、无日志。当前 13 个 dict-read 文件全为 md/json（未触发），但契约未禁止对 `.yaml`/`.txt` truth 文件声明 fields（truth-files.index.json 含 `import/source/*.txt` 等）。
- **影响**：一旦有人对非 md/json 文件声明 fields，过滤与 escape hatch 语义双双静默失效（与 T301 叠加则永远无感知）。
- **建议**：非 md/json 且 fields 非空时 log WARN（"field_filter_unsupported_ext"）或实现 YAML 键过滤。
