## 二、finish_reason 与 429 一致性（PR #40 后）

### 2.1 finish_reason 三路径对照

| finish_reason | API 路径（:1564-1644） | IDE 路径（codex/zcode） | legacy CLI 路径 |
|---|---|---|---|
| `stop` | 放行 → parse/write | 无概念（prose + `### FILE:` 解析） | 无概念 |
| `length` | cap-raise 1 次（×2，上限 `_MODEL_OUTPUT_CEILING`×0.9=58982）→ 仍 length 则 fail-fast（:1621） | **无截断检测**：截断输出按 `### FILE:` 解析，部分写入后 missing 仅 log.error、返回 success（:1770-1783） | 同 IDE |

- PR #40 只给 API 路径加上了 length→cap-raise 与 content_filter→fail；IDE/legacy 路径**没有任何截断检测**——spec §5.1 的 cap-raise 保护在 IDE/legacy 路径不存在，截断的章节草稿经 IDE 路径会被静默接受为成功（F375 的 missing 检查是 log-only、非阻断）。
- `test_dispatch_helper_finish_reason.py` 只测 `_call_llm_streaming` 的 chunk 采集，无任何测试断言 `_dispatch_via_api` 对三值的端到端分支（cap-raise 测试用 MagicMock 直 mock `_call_llm_streaming_with_retry` 返回值，跳过真实流）。

### 2.2 429/速率限制覆盖

- 全仓无 `Retry-After` 头处理（grep 0 命中）；无 openai `RateLimitError` 专门分支。
- 唯一 429 感知层是 tenacity `_is_retryable`（`_RETRYABLE_STATUSES={429,500,502,503,504}`）——**生产不可达（T501）**。
- 并行波有 Semaphore(4) 限并发 + 1-3s 退避（R8），但退避量级不足以应对 DeepSeek 常见的 429 窗口。
- 串行路径 429 → 立即重发全量 prompt（T503）。

## 三、findings（T5xx）

### T501 · [P1] tenacity 重试层在生产路径为死代码：`_is_retryable` 只认裸 httpx 异常，openai SDK 异常永不命中（429/5xx/timeout 零重试 + 测试掩盖）

- **证据**：`_is_retryable`（dispatch_helper.py:1370-1376）只检查 `httpx.TimeoutException` / `httpx.HTTPStatusError`。生产唯一调用路径 `_dispatch_via_api`（:1518-1521）用 `openai.OpenAI` SDK；SDK v2.44.0 把所有传输错误包装为自己的层级：`openai.RateLimitError`（429）、`openai.InternalServerError`（5xx）继承 `openai.APIStatusError`，`openai.APITimeoutError` 继承 `openai.APIConnectionError`——**都不是** `httpx.HTTPStatusError`/`httpx.TimeoutException`。运行时 probe 实测：`_is_retryable(openai.RateLimitError(...)) = False`、`_is_retryable(openai.APITimeoutError(...)) = False`、`_is_retryable(openai.InternalServerError(...)) = False`；仅裸 httpx 异常返回 True。`@retry` 装饰器（:1441-1443）因此永不触发，`before_sleep` 的 `llm_retry` 日志、指数退避、3 attempts 全部空转。
- **测试掩盖**：`tests/pipeline/test_retry.py` 用 `httpx.HTTPStatusError`/`httpx.TimeoutException` 模拟（:28-33/:48-50/:63-64/:75-76/:89）——与生产实际异常层级（openai SDK）不符，测试全部通过但掩盖了接线断裂。
- **影响**：模块 docstring（:1460）明示 "Retries: 429 (rate limit), 5xx (server errors), timeouts" 为假；429/5xx/timeout 直接穿透为 DispatchResult 失败 → 落入无退避的 pipeline 级重试（T503 放大）；指数退避（唯一像样的退避）从不运行；对 DeepSeek 等常见限流 API，rate-limit 风暴下每次失败都立刻整体重发。
- **建议方向**：`_is_retryable` 增加 `openai.APIStatusError`（`exc.status_code in _RETRYABLE_STATUSES`）与 `openai.APITimeoutError`/`openai.APIConnectionError` 分支（probe 验证可行）；测试改为断言 openai SDK 异常路径（或对 SDK 层做集成桩）。

### T502 · [P1] ESCALATION 解决不清零 durable 重试预算：升级后首个再失败确定性 raise 未捕获 RetryExhaustedError（F304 崩溃的第二触发源 + machine.py 契约假）

- **证据**：`machine.py:85-93` `clear_checkpoint` 对 ESCALATION 的 APPROVE/REJECT/MODIFY 只清 `retry_counts`（:90-92），**不清 `retry_budget_consumed`**；后者全仓只增不减（grep：chapter_loop:614-615/2879-2880 累加、state_heal:34 播种、无任何 pop/clear/重置）。运行时 probe：3 次失败 → ESCALATION → APPROVE（`clear_checkpoint` 后 `retry_counts={}`、budget=3）→ 同 step 再失败 → `_handle_failure`（chapter_loop:613-618）`consumed=4 > 3` → **raise RetryExhaustedError**。该异常穿透 `run_chapter_step` → cli `cmd_next`/`cmd_resume`（:602-604 仅捕 FileNotFoundError）→ 裸 traceback，且 `save_state` 未执行（F304 已记崩溃形态）。
- **根因**：`clear_checkpoint` 的 "fresh set of retry attempts"（machine.py:72-74 docstring）只重置了 ephemeral 层，durable 层（spec §3.1 为 crash-resume 设计）在**人工升级裁决（human override）后也应归零**——否则升级流程结构性无法给出新的重试机会：F304 建议的"CLI 捕获转 ESCALATION"会把崩溃变成"升级→批准→再失败→再升级"的永动环。
- **影响**：正常（非崩溃）升级流程中，任何在第 3 次失败后被人工解决的步骤，一旦重跑再失败即裸崩；审计 BLOCKING 环同族（`cs.audit_retry_count` 同样在升级后不重置，chapter_loop:2941 从 3 继续 → 立即再 ESCALATION）。
- **测试掩盖**：`tests/unit/pipeline/test_retry_budget.py` 只测 `_reset_retries` 不清 budget、以及预算超限 raise（monkeypatch 使 handle_dispatch_failure 恒 True），无任何测试覆盖 `clear_checkpoint` + resume + 再失败的端到端序列。
- **建议方向**：`clear_checkpoint` 的 ESCALATION 分支同时清 `retry_budget_consumed`（与 retry_counts 同步）；或 `_handle_failure` 在 `consumed > max` 时改设 ESCALATION checkpoint 而非 raise（F304 同向）。

### T503 · [P2] pipeline 级重试无退避、无失败分类：串行/closure 立即连发 ≤3 次全量 dispatch，429 风暴与 content_filter 等不可重试失败被同等放大

- **证据**：① cli `_orchestrate_to_checkpoint` `while True`（:200-270）：`run_chapter_step` 返回 False（重试）后**立即**进入下一轮 `run_chapter_step`，无任何 sleep；genesis 同循环。② closure `run_closure_step` `while True`（:252-275）在单次调用内连发，同样无退避。③ `_handle_failure`/`handle_dispatch_failure` 对失败类型零区分：content_filter 拒绝（不可重试）、写失败（T504）、确定性 G4 FAIL、429（可重试）全部走同一 3-attempt 立即重试预算。④ 放大：API 路径 cap-raise 是第二次全量调用（:1597），最坏 3 pipeline attempts × (1 截断 + 1 cap-raise) = **6 次全量输出**（每次 ~31KB，F8/F317 已记 token 浪费面）；429 场景在 T501 死码下无退避直发 3 次。
- **对照**：唯一有退避的层是并行波（parallel_dispatch:117-125，`2^n + uniform(0,2)` 1-3s）——量级不足以让 429 冷却。
- **影响**：限流风暴下放大 429（重发即再 429）；不可重试失败（content_filter/政策拒绝）重复烧 token 后照常升级；pipeline 文档/spec §11 只字未提退避。
- **建议方向**：pipeline 级重试加入退避（与 T501 修复后的 tenacity 层错开，如 5/15/45s）；`handle_dispatch_failure` 增加失败分类（可重试 transient vs 不可重试 policy/确定性失败，后者直接升级）。

### T504 · [P2] 写失败重试反馈 dead-wire：`build_retry_feedback`/RETRY_WRITE_CONFIRMATION 进 `DispatchResult.stderr`，无编排方读 stderr 注入重试 prompt → 写失败盲重试 ×3

- **证据**：`_write_parsed_outputs`:1106 raise `DispatchWriteFailureError`（携带 signature）；API（:1657-1663）/IDE（:1760-1766）路径捕获后 `return DispatchResult(False, -1, "", build_retry_feedback(exc))`——反馈落在 **stderr 字段**。编排方对 stderr 的消费：genesis:305-307 仅 log；parallel_dispatch:104 仅 log；chapter_loop/closure **完全不读**。重试 prompt 的反馈注入只读 `state.chapter_loop.retry_feedback` / `state.genesis.retry_feedback`，而这两个 dict 只在 **G4 失败**路径写入（chapter_loop:2877 `_enrich_g4_feedback`、genesis:324）。grep 证实 `RETRY_WRITE_CONFIRMATION` 在 dispatch_helper/llm_output_integrity 之外零引用。
- **影响**：模型输出沙箱诊断 → 检测 → 重试时收到的是**原 prompt**（无 "You have filesystem write access" 确认语）→ 大概率重复同样的诊断 → ×3 后升级。spec 设计的"写能力确认纠正环"从未生效；`DispatchWriteFailureError.signature` 字段是死数据。
- **建议方向**：`_handle_failure`/dispatch 调用方把 `DispatchWriteFailureError` 反馈写入 `retry_feedback[retry_key]`（与 G4 反馈同一注入通道），或 API/IDE 路径直接以 `retry_feedback` 返回。

### T505 · [P2] finish_reason 处理仅 API 路径实现：IDE/legacy 无截断检测（cap-raise 保护缺失），finish_reason=None 时截断不可检测

- **证据**：API 路径实现 length→cap-raise 一次→fail-fast、content_filter→fail（dispatch_helper:1564-1644）；IDE 路径（:1695-1783）与 legacy 路径（:1843-1880）对截断零检测——codex/子进程输出的部分文件被 `_write_parsed_outputs` 照常写入，missing 检查（:1770-1772）log.error 后**仍返回 DispatchResult(True)**（F375 同族：部分缺失被接受）。此外 API 路径对 `finish_reason is None`（末块缺失/early_stop 打断，:1416-1418 + :1642-1644 fall-through）当作成功放行：截断 JSON 进 `_parse_structured_output` → FILE-marker 回退 → "No output files written" 失败 → 盲重试，截断本身无日志信号。
- **影响**：spec §5.1 的"截断保护"只在 API 路径成立；IDE/legacy 路径截断章节静默落盘（行为分叉）；finish_reason=None 使 length 检测失效（依赖 provider 末块行为）。
- **建议方向**：IDE/legacy 路径对"声明输出文件缺失/过短"升级为失败（与 F375 修复合并）；API 路径在 finish_reason=None 且输出明显不完整（无 stop 信号）时按截断处理或至少 WARN。
