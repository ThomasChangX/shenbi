### 1.2 pickle 边界结论：**全仓无 ProcessPool / multiprocessing / joblib / pickle / cloudpickle**

`grep` 全仓（src/tests/tools/skills）0 命中 `multiprocessing`、`ProcessPoolExecutor`、`pickle`、`joblib`、`dill`、`cloudpickle`。**不存在 pickle 边界**——无跨进程对象序列化。全部子进程边界均为 argv/stdio 字符串协议：

1. `dispatch_skill` legacy 路径：`subprocess.run(["uv","run","shenbi-dispatch", skill, test_type, rd, prompt])`（dispatch_helper.py:1864）
2. `run_gate_g4/g3`：`subprocess.run([sys.executable, "-m", "shenbi.gates.cli", ...])`（dispatch_helper.py:1896-1905, 1947）
3. IDE 路径：`subprocess.run([codex, exec, ..., "-"])`，prompt 走 stdin（dispatch_helper.py:1735）
4. `phase_runner.run_gate`：同 2（phase_runner.py:87）

→ 因此"函数/闭包/lambda/本地类经 ProcessPool 传递不可 pickle"类问题**不存在**；并发风险全部集中在**进程内共享状态 + 跨进程文件锁两域**。唯一可跨进程共享的"对象"是文件（JSON/JSONL/MD），其竞态面见 §二/三。

## 三、交叉验证（引用已知 findings，非新增）

1. **F326 补充证据（不重复录入）**：并行 post-draft 的 `run_parallel_post_draft_steps` docstring 声称 "Both steps ... write to disjoint files: lifecycle -> pending_hooks.md, state-settling -> 6 truth files. Zero data conflict." —— **该断言与契约矛盾**：契约扫描显示 `shenbi-state-settling` 的 `updates` **也含 truth/pending_hooks.md**（共 7 个目标，非 6 个）。即 pending_hooks.md 在并行波内**有两个整文件写者**，后写者确定性覆写先写者（lost-update）。F326 的机制由此钉死（两 worker 均 `uses_staging=True` → 竞态发生在 staging/truth/pending_hooks.md，review approve 提交后进入 truth/）。
2. **F374 佐证**：resonance 确在并行波（CHAPTER_STEPS[13] `is_audit=True`，`core_skills` 按 `"review" in skill` 选中），且契约 `updates: truth/audit_drift.md + truth/resonance_trend.md` —— `assert_parallelizable` 对它放行，写入走 `_write_parsed_outputs` 整文件路径。T6-03 为其根因与 arc-payoff 潜伏扩展。
3. **F505/F3A4/F253 家族**：本轮复核确认同构问题在 pipeline-manifest.json（T6-01）再次出现——"线程锁不跨进程 + 读-改-写"模式是第 4 个实例站点。
4. **TraceWriter**：`trace/writer.py:4-6` 自述 "NOT thread/proc-safe — __init__ reads then append writes (TOCTOU)"，当前全部调用点（safe_write 带 trace 参数 / audit/record.py / migrate.py）都在主线程；并行路径的 safe_write 均不带 round_dir/trace_action → 无现行并发触发。保持观察项，不升级。
5. **`PipelineState._lock` 覆盖缺口**：`_record_token_usage`（dispatch_helper.py:1325-1329）对 `state.token_usage` 的 `+=` 复合更新**不持锁**，但经核查全部调用点在主线程（并行波/并行 post-draft 的 dispatch_skill 均不传 state）→ 无现行并发；若未来并行路径传 state，即变成裸竞态（建议顺手加锁或并入 F302 修复时处理）。

## 四、结论

**新 finding 数：5**（T6-01 P2、T6-02 P2、T6-03 P2、T6-04 P2、T6-05 M；无 P0/P1）。

**并发模型总评**：
- **无 pickle 边界**：全仓无 ProcessPool/multiprocessing/pickle，子进程边界全是 argv/stdio 字符串协议——"函数/闭包不可 pickle"类风险不存在。
- **进程内**：共享可变状态极少（并行 worker 均不传 `state`，`SharedAuditContext` 只读），`PipelineState._lock`/truth_io 路径锁/信号量覆盖了主要线程面；残余问题为两个无锁缓存（T6-02 已复现）与锁键未规范化（T6-04）。
- **跨进程**：主风险仍是"读-改-写 + 线程锁不跨进程"家族——F253（progress.json）/F3A4（integrity-findings）之后，pipeline-manifest.json（T6-01）是第 4 个实例；safe_write 的 flock 只保护单次写，不保护任何读-改-写事务。
- **锁一致性**：safe_write 的 flock（目录级）与 O_EXCL 回退（文件级）互斥粒度不对称（T6-05）；写安全分类（write_safety.py）依赖名字启发式，2/26 review skill 已证伪其谓词（T6-03），`assert_parallelizable` 的结构性保证需要改为契约驱动。

**最终消息**：新 finding 5 条（T6-01~T6-05，均 P2/M），无 P0/P1；pickle 边界结论=不存在（无 ProcessPool）；并发安全主要缺口集中在跨进程读-改-写（manifest 第 4 实例）与写安全分类谓词（2/26 反例，含 arc-payoff 潜伏扩展）。
