## 二、Findings

### T506 | 429/瞬时失败实为三层互不协调重试：SDK 隐式 max_retries=2（尊 Retry-After）× tenacity（死层）× parallel 外层——F977 的"零重试"表述需修正，且修复若不加约束将放大为 27 请求/任务 | 退避缺陷/参数 | P2

**证据**:
- 实测（/tmp/t5x/ 探测）：`openai==2.44.0` 客户端默认 `max_retries=2`、`_base_client._should_retry` 覆盖 408/409/429/5xx 并尊 `x-should-retry`/`Retry-After`；`dispatch_helper.py:1539-1542` 构造客户端时未覆写 `max_retries`。
- tenacity 层谓词死（F977 verified：`_is_retryable` :1383-1389 仅 httpx 两分支）。
- parallel 外层：parallel_dispatch.py:77-128 对 `DispatchResult.success=False` 与异常同样盲重试 ×3；且 `_dispatch_via_api` **每次调用新建 OpenAI 客户端** → 外层每轮重试将 SDK 内层重试预算重置。
- 全仓 grep `retry-after|Retry-After` 零命中——编排层无一处解析 Retry-After。

**根因**: 重试架构三层叠加但无单一 owner；F977 只审了 tenacity 一层。

**验证**: 上述探测命令可直接复跑（uv run python -B 探测 openai SDK）；行号见证据。

**影响面**: 持续 429 下单审计任务 = 外层 3 × SDK 3 = 9 个 HTTP 请求（Semaphore(4) 并发下风暴倍增），且外层退避 [1,3]+[2,4]s 远小于常见 Retry-After（数十秒）→ 外层重试大概率撞同一限流窗。**若 F977 按字面修复（扩展 `_is_retryable` 认 openai 异常）而不设 `client max_retries=0`**：3×3×3=27 请求/任务。

**建议方向**: F977 修复必须三选一定 owner：(a) 客户端 `max_retries=0` + tenacity 统管（需 tenacity 侧解析 Retry-After）；(b) 信任 SDK 层（删 tenacity 或仅保留非 429 用途）；(c) 外层降为 1 次并延长退避至 ≥Retry-After 量级。任一方案都应消除新建客户端导致的预算重置。

### T507 | `_dispatch_via_api` 把一切 API 失败当超时处理：`except Exception` 无条件调 `_handle_timeout_gracefully`，日志谎报 `dispatch_timeout`/`resolution=saving_partial_output`（实际什么也不保存） | 异常吞掉致错误分类 | P2

**证据**:
- dispatch_helper.py:1569-1572：`except Exception as exc: _handle_timeout_gracefully(skill, chapter); log.error("api_call_failed", ...)`。
- `_handle_timeout_gracefully`（:123-132）只发一条 WARN `dispatch_timeout, resolution="saving_partial_output"`——docstring 称 "Save partial LLM output"，实际**无任何保存动作**（注释自认 "logged for observability; actual handling depends on skill"）。
- 对照：cap-raise 二次调用（:1629-1635）已正确用 `"timeout" in str(exc).lower()` 分类后才调用；IDE/legacy 路径（:1767-1770/:1911-1914）只在 `subprocess.TimeoutExpired` 调用。唯独 API 主路径的 catch-all 未分类。
- 次生链：日志事件名含 "dispatch" → run_pipeline.sh:93-102 的 grep（escalation/gate/dispatch → auto-approve）会把 429/401/content_filter 引发的升级一并自动批准（F002 为根，此条提供触发面）。

**根因**: 超时处理函数被复用为通用失败钩子；`resolution` 字段是行为谎言。

**验证**: 行号直读；`_handle_timeout_gracefully` 函数体 10 行无 I/O。

**影响面**: 故障归因失真（429 风暴/密钥错误/content_filter 在日志里全是"超时"）；运维脚本基于错误日志的自动决策链被污染。

**建议方向**: catch-all 内按异常类型分类（APITimeoutError→timeout 路径；其余→api_error），删除或落实 "saving_partial_output"。

### T508 | `audit_retry_count` 无任何重置路径：ESCALATION 解决后首个再 BLOCKING 立即再升级、永不再尝试 revision——与 machine.py "all per-phase retry counters are reset" 契约直接矛盾 | 正常路径功能错误（checkpoint 解决机制对审计阻塞失效） | P1

**证据**:
- 唯一递增点 chapter_loop.py:2978（`cs.audit_retry_count += 1`）；全仓 grep 该字段：无任何 `= 0` / `pop` / 清零路径（state.py:102 定义、:251/:314/:397 序列化往返，state_heal.py 不触及）。
- `clear_checkpoint`（machine.py:85-93）只清 `genesis.retry_counts`/`chapter_loop.retry_counts`/`closure_retry_counts` 三个 dict——**不含** ChapterState.audit_retry_count；`_reset_retry_budget`（cli.py:524-541，REJECT 路径）也只清两个 dict。APPROVE/REJECT/MODIFY 三种决定均不重置。
- 行为推导（代码路径直读）：审计阻塞升级（:2987-2996，audit_retry_count=3 持久化）→ 人工解决 checkpoint → 重跑该 step → :2968 `while 3 < 100` → run_audit_layer 再 BLOCKING → 计数 4 → `handle_audit_blocking(4)`（error_handler.py:71-81，4 < 3 为 False）→ **不派发 revision 直接再 ESCALATION**（:2981-2996）。MODIFY 反馈只注入下一个 step 的 dispatch prompt（:2811-2817），对审计层无效。
- machine.py:73-74 docstring："all per-phase retry counters are reset so the pipeline gets a fresh set of retry attempts"——对 audit_retry_count 为假。

**根因**: 审计 revision 环的预算计数器遗漏在两套重置机制（clear_checkpoint / _reset_retry_budget）之外。

**验证**: `grep -rn 'audit_retry_count' src/` 全部 9 处逐一核对（无重置）；while 环与 handle_audit_blocking 阈值逻辑直读。

**影响面**: 任何走到"审计 BLOCKING 3 轮→升级"的章节，升级解决后自动 revision 能力永久丧失（除非审计一次通过）；叠加 F002 的 auto-approve 即成 approve→重跑→再升级的空转循环。Z11 盘上 56 章 audit_retry_count 全 0 属另一问题（F1103/F1174 计数不回写），与本条"无重置路径"互不影响。

**建议方向**: `clear_checkpoint` 的 ESCALATION 分支与 `_reset_retry_budget` 同步清 `cs.audit_retry_count`（按 chapter 定位）；或把该计数器并入 retry_counts 体系。

### T509 | 截断产物写穿（实测）：`_parse_file_markers` 接受截断的 `### FILE:` 输出并直接落盘——IDE/legacy 路径无 finish_reason 保护，.md 无任何完整性守卫（T505 断链重立 + 后果面新证） | 覆盖缺口/静默错误产物 | P2

**证据**:
- 实跑（/tmp/t5x/trunc_test.py，只导入 src 不写仓库）：向 `_parse_structured_output` 输入"第二个 FILE 块从中间被截断"的多文件响应，解析出 2 个文件，末文件内容止于 `'- hook2: TRIGGERED (伏笔：玉'`（半个中文字符处）——**截断被静默接受**。decisions.json 的两道守卫（raw_decode + DecisionsDoc schema）实测均正确拒绝（对照验证）。
- 落盘链：`_write_parsed_outputs`（dispatch_helper.py:1057-1196）对 .md 只做 write-failure 检测 + 尺寸守卫；写后仅查 `missing`（文件存在性，:1688-1691/:1799-1801），不查完整性。
- 保护面：API 路径有 finish_reason=length 的 cap-raise/fail-fast（:1586-1654，PR #40，T10 已核）；**IDE 路径（:1716-1812）与 legacy CLI 路径（:1881-1925）仅凭 returncode**——本仓库环境 codex 在 PATH 上，无 API key 时 IDE 即默认路径。
- finish_reason=None 时 API 路径同样无保护（T505 已述；不重复合并）。

**根因**: 完整性守卫只建在 decisions.json（schema 可验）与 finish_reason（仅 API 可见）两个信号上；.md 多文件标记解析器天然接受 `\Z` 截断尾。

**验证**: 上述实验可复跑；`_parse_file_markers` 正则 `(?=###\s*FILE:|\Z)`（:905）结构上即接受截断。

**影响面**: IDE/legacy 下流式/子进程输出被截断时，截断的章节/真相文件静默落盘（G4 字数下限 4000 仅对章节部分兜底；plans/audits/truth 无长度门）。若项目以 IDE/legacy 为主执行路径，此条应升 P1。

**建议方向**: IDE/legacy 写盘前做终末标记校验（如要求最后 FILE 块以非截断哨兵结尾），或对 .md 加最小结构检查；与 F1116（trace 无 finish_reason 字段）联动补计量。

### T510 | 确定性失败被全层盲重试（量化）：length_persistent / at_ceiling / content_filter 等不可重试失败在 parallel（×3，有退避）与 chapter_loop/genesis/closure（×3，零退避）被逐层放大，length 路径每 attempt 2 次全价调用 → 单步最多 6 次全价 LLM 调用（T503 实质重立 + 层数学） | 重试经济/退避缺陷 | P2

**证据**:
- 确定性失败信号：`length_truncation_persistent`（:1642-1654）、`length_truncation_at_ceiling`（:1595-1610）、`content_filter`（:1586-1590）均返回 `DispatchResult(False)`，stderr 文本可判确定性——但所有外层只看 `success` 布尔。
- parallel 外层（parallel_dispatch.py:92-128）：success=False → 盲重试 ×3（审计场景：3×2=6 次调用后静默交败，F309 已覆盖后续静默放行）。
- chapter_loop 串行层（chapter_loop.py:2864-2871 → `_handle_failure` :587-671）：重试 ×3 **零退避**（`return False` → cli.py:195 `while True` 立即重入）；length 类失败每次 attempt = 原始 cap + cap-raise 两次调用 → 6 次全价调用。drafting 场景单次失败链成本 ≈ 6×(输入~数万 + 输出≤58982) tokens。
- genesis/closure 同构（genesis.py:330 / closure.py:207-239，均零退避）。
- 对照组：cap-raise 自身有界（max 1 resend，spec §5.1）——有界性正确，错在**层间无失败分类传递**。

**根因**: DispatchResult 无 failure_class 字段；各层独立决策同一失败。

**验证**: 行号直读 + 全景表 O2/O5/O14。

**影响面**: "章节对模型输出上限过长"这类确定性根因，每个审计/串行重试点都全额付费验证一遍；429 风暴（T506）下零退避串行层还是放大器。

**建议方向**: DispatchResult 增加 `deterministic: bool`（length_persistent/at_ceiling/content_filter/GATE_FAIL 置位），外层见位即停；串行层补最小 sleep。

## 四、总结

1. **全景规模**: 24 个生产重试/退避/超时参数点，分四层——传输层 3 套互不协调的重试机制（SDK 隐式 / tenacity 死层 / parallel 外层）、编排层 8 类重试点（其中串行三层零退避、scoring 路径无界）、门禁/锁 6 点、输出上限 4 点。RETRY_JITTER=2.0 在仓库内是唯一显式 jitter 常量且量级合规（与 base 2.0 同阶，PR #40 修复有效），但三套 jitter/退避互不感知。
2. **新增 findings**: 9 条（T506-T514）——P1×1（T508 audit_retry_count 无重置路径）、P2×6（T506 三层重试架构、T507 失败分类坍缩为超时、T509 截断写穿、T510 确定性失败全层盲重试、T511 scoring 无界重试、T512 写失败反馈 dead-wire）、M×2（T513 异常体系使用率、T514 杂项）。另有 2 条上轮断链重立（T509/T510/T512 含 T505/T503/T504 实质）。
3. **最大重试经济问题**: 确定性失败（章节超模型输出上限、content_filter、GATE_FAIL）没有任何跨层失败分类，被 parallel ×3 + 串行 ×3 逐层全价盲重试（length 路径单 attempt 即 2 次调用），单步最多烧 6 次全价 LLM 调用去"验证"一个已知必然失败的结局——而唯一的 jitter 常量 RETRY_JITTER=2.0 只保护了审计并行层这一小段。
