## 一、六任务域结论一览

### ① 热路径复杂度标注（chapter_loop.py + dispatch_helper.py + 支撑模块）

每章 16 步循环体的每步成本结构（静态推导，实测数标注）：

| 步骤 | 主导操作 | 复杂度 | 超线性点 |

| 2 chapter-planning | **误触发装配+策展**（T1602）+ LLM 派发 | 每章 2×装配 | 装配内 build_index O(T)×2/章 |

**truth 全量重读 vs 增量读**：dispatch 层每次派发按契约 reads 全量重读文件（dispatch_helper.py:580-608，无 mtime 缓存）；字段级过滤（Layer B）只对声明了 `fields:` 的读取生效，review-group-factual 对 `truth/chapter_summaries.md` 为裸字符串读取（无窗口无过滤）。共享审计上下文（audit_context_cache）本应消重 I/O，但 chapter_text/volume_context 两条路径写死错误位置（F312），实测章节文件仍被读 8 次/章（T1614）。
**上下文组装拼接策略**：`_budgeted_truncate` 按权重分配 + join 一次性拼接，无逐字符扩容问题；流式 `_call_llm_streaming` 的 early-stop 分支存在逐 chunk `"".join(collected)` 的 O(k²) 潜在点，但生产无调用方传 early_stop_patterns（死参数，不立案）。
**审计波每波扫描集**：`_get_audit_history` 每章遍历全部历史 chapter_states（内存，O(N)/章 → O(N²) 总，纯内存且常数极小）；`_any_audit_has_findings` 每章 ≤13 文件定点读，O(1)/章。
**契约幂等重算**：`load_contract`→`load_registry` 无任何缓存（全仓 lru_cache 为 0，唯一 grep 命中是注释），每次派发、每个门禁子进程、每次 requires_independent 都重解析 9KB registry YAML + pydantic 验证（实测 26.5ms/次，为 _build_skill_prompt CPU 的 98%——T1613/F215 增量）。

## 二、Findings 详情

### T1601 | 审计波上下文重复注入：8/10 派发各自内嵌全章文本，章节文本重复占每章 prompt 体量 29% | token 浪费 | P1

- **证据（实测）**：/tmp/t16/full_chapter_prompts.py，真实项目 ch30（31.1KB=11,674 字符）。10 个每章派发（planning/drafting/lifecycle/settling/4 审计组/resonance/sensitivity）prompt 总量 320,764 字符（~107K tok/章）；中章探针命中 **8/10** prompt 内嵌全文；章节文本重复 8×11,674=93,392 字符 = **29%**。叠加 genre-config ×5、pending_hooks ×3、plan ×3、SKILL.md 系统段各携（group-factual 单 prompt 实测 53,767 字符）后，共享内容重复份额 ≥40%。
- **增长曲线**：章节长度 ×2 → 审计波 prompt 体量 ×2（每份内嵌线性）；章数 ×2 → 总冗余 token ×2（比例恒定 ~29%，在 `_INPUT_MAX_CHARS_TOTAL=128K` 截断内不衰减）。56 章已付 ≈0.29×107K×56 ≈ **1.74M tok 冗余输入**。
- **标注**：实测。
- **影响面**：每章审计波全部 6 技能 + drafting/lifecycle/settling；API 计费输入侧；长书成本线性放大。
- **建议方向**：MERGE-2 已把 13 审计并成 6 组，下一步二选一：(a) 组间共享前缀固定化（章节文本置于 system/首 user 段固定位置），利用 provider 前缀缓存（DeepSeek context caching）；(b) 审计波改单次多报告派发（6→1，输出段分隔）。

### T1602 | 步骤 2（chapter-planning）误触发上下文装配+策展：计划文件尚不存在 → 空跑装配+fallback 写盘，每章 2× Route B 网络停顿 | 热路径冗余 | P1

- **证据（静态推导+实测）**：chapter_loop.py:134-161 中 CHAPTER_STEPS[1]（shenbi-chapter-planning）与 CHAPTER_STEPS[2]（pipeline-context-prepare）**均**置 `calls_context_assembly=True`；:2749-2752 对两者都执行 `_run_context_assembly` + `_run_context_curation`。步骤 2 的装配读 `plans/chapter-N-plan.md`（context_assemble.py:287 直接 read_text）——该文件由步骤 2 自己产出 → 首跑抛 FileNotFoundError（:1181-1182 捕获告警）→ `_write_minimal_context_fallback` 写盘（:1185-1187），步骤 3 再整体重做并覆盖。F311 已立案 curated 死输出，本条增量是**执行次数**：装配+策展每章各跑 2 次。Route B 停顿实测 3,530/266/490ms（/tmp/t16，见 T1603）→ 每章 2×0.3-3.5s 纯网络空转。

- **标注**：静态推导（双触发点行号）+ 实测（route_b 延迟、assemble_context 3495.8ms）。
- **影响面**：每章 2 次装配/策展/写盘 + 双网络停顿；56 章项目 ≥6.5 分钟纯停顿外推。

### T1607 | 差分快照每章全量重哈希 chapters+audits+plans：实测 43-49ms@N=56（923 文件/10.2MB），累计 O(N²) 字节重读 | 非热路径超线性 | P2

### T1608 | save_state 每步全量 dump：132KB×~16 次/章@N=56，状态体积 ∝N（含 F368 滞留的 retry_feedback 54 条）→ 累计写体量 O(N²) | 非热路径超线性/重复 I/O | P2

## 四、总结

1. **最大超线性点**：token/IO 双料——审计波上下文重复（T1601，29% prompt 体量即期浪费、比例恒定）与差分快照/save_state/前章标题三处 O(N²)（T1607/T1608/T1609，绝对值尚小但增长律明确）；唯一随 N 超线性增长的 **token** 项是累积 truth 全文注入（T1615，N×2→×4）。
2. **最大的即期固定浪费**：T1602（每章 2×装配+双网络停顿）与 T1604（每章 ~1.7s 门禁 import 开销）——均为"每章常量、全书线性"，修复成本低（去一个 flag / lazy import）。
3. **可观测性**：token 台账与 prompt 指纹在生产项目完全缺失（T1611），所有 token 比例结论只能由确定性 prompt 重构侧证实；建议先补记录面再谈命中率。
4. 修复优先序建议：T1602（一行 flag）→ T1604/T1613（lazy import+registry mtime 缓存）→ T1601（前缀缓存/单派发多报告）→ T1607/T1608（增量哈希/游标持久化）→ T1615（滑动窗口）。
