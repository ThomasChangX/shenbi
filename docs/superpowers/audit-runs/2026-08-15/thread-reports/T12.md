### T1201 | 审计报告决策解析器无作用域 first-match：被审章节文本经证据引用伪造 G4 判定与共振分数（gate/路由完整性） | security | P1

### T1203 | run_pipeline.sh 的 STATUS/PHASE 解析可被 console 渲染的 agent stderr 预览污染：崩溃路径无机器状态行时被审/代理内容决定循环分支 | security | P2

- **证据**（实跑，`/tmp/t12/poc5/spoof_demo2.sh` 复刻 run_pipeline.sh:26-28 解析逻辑）：
  ```
  parsed STATUS=ok PHASE=completed CP=chapter_memo
  ```
  输入 = emit_json 状态行（`"status": "blocked"`）+ structlog **console 渲染**（默认格式）的 `ide_failed` 事件（dispatch_helper.py:1776 `log.error("ide_failed", ..., stderr=r.stderr[:500])` 原样内嵌 codex/zcode 代理 stderr，其中含代理输出的 `{"status": "ok", "phase": "completed"}` 文本）+ Traceback。`grep -o | tail -1` 取最后匹配 → 代理文本胜出。
- **崩溃路径实证（读码）**：`cmd_resume` 仅捕获 FileNotFoundError（cli.py:853-857 `except FileNotFoundError`），其他异常直接 traceback、**无 emit_json**——OUTPUT 里根本没有机器状态行，最后一条 `"status": "` 完全由日志/代理内容决定。
- **与 F002/F1014 叠加**：`error|failed` 分支 grep "escalation\|gate\|dispatch" 自动 approve（F1014）+ STATUS 被污染成 ok → `PHASE=completed` 时脚本打印 "PIPELINE COMPLETED SUCCESSFULLY!" 并 exit 0（run_pipeline.sh:46-49）——崩溃的管线静默"成功"退出；或 STATUS=ok 继续循环跳过 checkpoint 审查。
- **JSON 日志模式复核**：`SHENBI_LOG_FORMAT=json` 下 structlog 行的 `\"status\"` 带反斜杠转义不匹配 grep 模式（实跑确认），但 gate 结果类事件（audit_layer.py:179 `g4=g4`、genesis.py:366 `g3=g3`）以 JSON dict 值形式携带 `"status": "FAIL"` 仍可匹配——两种日志模式各有污染面。
- **根因**：stdout（emit_json 数据）与 stderr（structlog 诊断，内嵌代理输出预览）被 `2>&1` 合流后用文本 grep 提取决策字段；last-match 无来源约束。
- **影响面**：仅 run_pipeline.sh 包装层（非默认入口，需显式使用）；结合 F002 无人值守场景被放大。
- **建议方向**：`uv run pipeline resume` 只取 stdout（`2>/dev/null` 或分流 stderr 到文件）；STATUS 解析限定 emit_json 单行 JSON（`tail -1 | python -m json.tool`）；ide_failed 的 stderr 预览做控制字符/引号消毒再入日志。

## 四、总结
