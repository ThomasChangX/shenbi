## 2. Findings

### T401 | 落账单点被 state 双重门控，而记录点自身已具备全部所需输入——"传 state"是错误的修复形状 | dead-wire 架构 | P1

- **证据**:
  - 全仓唯一生产 `TokenLedger(...).record(...)` 调用点：`src/shenbi/pipeline/dispatch_helper.py:1346`，双重门控 `:1310 if state:` + `:1345 if project_dir is not None:`
  - 落账所需输入在记录现场全部可得：`_dispatch_via_api` 作用域内 `project_dir`（参数）、`skill`（参数）、`usage`（M1 返回）、`chapter`（`:1520-1524` 已从 path_ctx/extract_chapter 解析出 int|None）——`:1583` 调用点全部在握
  - E1 实验（`/tmp/t4x/e1_chapter_key.py`）：传 state 落账后 `chapter=0`（`getattr(state,"chapter",0)`，PipelineState 无该属性，真实值在 `state.chapter_loop.current_chapter`）；即 F301 的"传 state"修完后，by_chapter 依然全坍缩、只有 by_skill/total 被修复
  - legacy 分支收了 state 后静默丢弃（`:1881-1925` 无一处引用 state，也无 IDE 路径那样的提示日志）
- **根因**: 落账 API 把 durable 写（ledger append）与 transient 内存累计（state.token_usage）捆绑在同一个 state 门控之后；durable 写并不依赖 state。
- **验证**: 读码 + E1 运行输出（两行 ledger 记录 chapter 均=0）。
- **影响面**: F301 的修复方案设计；任何按"补传 state"推进的 PR 会做 10 处签名改动却只修复 by_skill 维度。
- **建议方向**: 在 `_dispatch_via_api` 内直接 `TokenLedger(project_dir).record(skill, chapter or 0, {...})`（chapter 用 `:1520-1524` 现成值），一处改动接通 13/13 API 调用点；state 仅留给内存摘要（或干脆废弃内存累计，print_token_summary 改读 ledger）。这与 T1611 的"三条路径统一传 state"建议相比改动面小一个数量级。

### T402 | durable ledger 的唯一消费端是手动 CLI：justfile/CI/管线收尾零调用，落账后仍无人读 | 报告面缺口 | P2

- **证据**: `render_report` 全仓调用仅在 `src/shenbi/cost/report.py:95`（CLI main）；`grep -n cost justfile` → 0 命中；章完成收尾只调 `print_token_summary(state)`（chapter_loop:948，内存态）；CI workflows 无 cost 步骤。
- **根因**: cost 报告从未接入任何自动面（just 任务/章末/per-chapter checkpoint/CI artifact）。
- **验证**: grep 三面（src/justfile/.github）。
- **影响面**: 即使 F301+T401 修复落账，成本可见性仍需人工敲 `shenbi-cost report`；F1115 类"零计量"事故的发现延迟不受改善。
- **建议方向**: 章完成时（chapter_loop:948 旁）追加 render_report 写 `cost/chapter-N-report.md`；justfile 加 `just cost <dir>`。

### T403 | 内存 token_usage 永不持久化：resume 后 print_token_summary 归零，与 durable ledger 语义分裂 | resume 累计缺口 | P2

- **证据**: `state.py:228-294 to_dict()` 显式字段列表无 token_usage；`from_dict`（:299-363）不恢复。E2 实验（`/tmp/t4x/e2_persist.py`）：记录 3000 tokens → save/load round-trip → `hasattr(state,'token_usage')=False`，`print_token_summary` 输出 0 行。
- **根因**: token_usage 是 `_record_token_usage:1327-1328` 用 `hasattr` 动态挂上的未声明属性，从未进入序列化面。
- **验证**: E2 运行输出。
- **影响面**: 长跑 + 多次 resume 的项目（生产 40h 运行正是此形态），章末 token 摘要只反映"本次进程"消耗，误导成本直觉；Z5-r3 曾核对的 resume 累计问题在内存面永远不成立，仅 ledger 面成立。
- **建议方向**: 随 T401 一并废弃内存累计（单一事实源=ledger），或把 token_usage 提升为 ChapterLoopStateData 字段并序列化。

### T404 | 未知 model 静默 $0 成本：_safe_estimate_cost 吞 ValueError，2M tokens 记为 $0.0000 | 静默错误结果 | P1

- **证据**: `ledger.py:23-34`（catch ValueError → log.warning → return 0.0）。E11 实验（`/tmp/t4x/e3_report.py`）：`SHENBI_LLM_MODEL=gpt-unknown-model` 下 `record` 2,000,000 tokens → `estimated_cost_usd=$0.0`，报告输出 `Total tokens: 2,000,000 ... Total cost: $0.0000`。
- **根因**: "ledger 绝不 crash dispatch"的韧性目标（合理）选择了把错误成本静默归零，而非在记录上标注 `cost_status=unknown`。
- **验证**: E11 运行输出（成本 0.0 + 报告 $0.0000）。
- **影响面**: 切换 provider/模型别名（PRICING 仅 1 个模型条目，pricing.py:22-24）即触发全量成本归零——报告面与 F1115 同级后果（成本不可信），且更隐蔽：有 tokens 有 calls，唯成本为 0。
- **建议方向**: record 增加 `pricing_status` 字段（priced/unpriced），report 对 unpriced 行显式输出 "cost N/A (model X unpriced)" 而非 $0.0000；保持不 crash。
- **注**: 决策表"静默错误结果"字面可上探 P0，因触发前提是模型配置偏移（非常规生产路径）且为新增 finding，定 P1 与 F1115 对齐，不单方降级任何既有条目。

### T405 | _try_avg_g3_score 吞并一切 `*score*.json` 数值：权重、检查计数混入 → cost-per-quality-point 无意义 | 报告面缺陷 | P2

- **证据**: `report.py:18-35`：glob `**/*score*.json`，取每个 dict 中所有 0-100 数值求均值。E12 实验：放入 `{vividness:72, logic:68, dialogue:91, weight:1}` 与 `{checks_passed:12, checks_failed:0}` → avg=40.67 → 报告输出 `Cost per quality point: $0.000771 (total_cost / avg_g3_score=40.7)`。
- **根因**: best-effort 启发式无 G3 语义过滤（不识别分数文件来源，不分字段名）。
- **验证**: E12 运行输出。
- **影响面**: 生产项目目录下任何同名文件（resonance 子分、gate 计数）都会扭曲该指标；报告消费者无从分辨。
- **建议方向**: 限定读取 gate manifest / progress.json 中已登记的 G3 分数字段；或字段名白名单（score/final_score）+ 文件名需含 g3。

### T406 | chapter 键坍缩传导至报告面："Per-chapter average cost" 恒等于总成本（单桶 0） | 报告面缺陷（F505 消费面印证） | P2

- **证据**: E1（全 ledger 行 chapter=0）+ E3：报告输出 `Per-chapter average cost: $0.0314` == `Total cost: $0.0314`（by_chapter 仅一个 "0" 桶，`sum/len` = total/1，report.py:68-72）。
- **根因**: F505（dispatch_helper:1348 chapter 恒 0）——本条不重复根因，只补消费面实证。
- **验证**: E3 运行输出两值相等。
- **影响面**: 报告的每章成本维度完全失义；修复 F505/T401 后自动缓解，但 report 对单桶情况无防御提示。
- **建议方向**: chapter 键随 T401 用记录现场值；report 对 `len(by_chapter)==1 && "0" in by_chapter` 输出警告行。

### T407 | TokenLedger 构造器在读取路径产生 mkdir 副作用 | 边界缺陷 | M

- **证据**: `ledger.py:56`（`__init__` 内 `mkdir(parents=True, exist_ok=True)`）。E4 实验：`summarize()` 前 `cost/` 不存在，之后存在。
- **根因**: 构造即建目录，读路径（summarize/report）共享同一构造器。
- **验证**: E4 运行输出 before=False / after=True。
- **影响面**: `shenbi-cost report` 对任意目录运行都会留 `cost/` 空目录；违背框架"纯校验无副作用"惯例（AGENTS.md Python 约定）。
- **建议方向**: mkdir 移入 `record()` 首写时惰性执行。

### T408 | TokenLedger._write_lock 跨实例无效：每次落账新建实例，锁从不互斥；并发安全实际依赖 O_APPEND 单行写 | dead-wire（假保护） | M

- **证据**: `dispatch_helper.py:1346` 每次 `TokenLedger(project_dir).record(...)` 新建实例 → 每把 `_write_lock`（ledger.py:57）都是新对象。E5(c)：两实例锁 `is not` 成立。E5(b)：8 线程 × 2000 次 fresh-instance append，16000 行 0 撕裂（APFS 实测 O_APPEND 单行写原子性兜底，但非该锁的功劳）。
- **根因**: 锁设计假设共享实例，调用面却是每调用一实例。
- **验证**: E5 运行输出（两轮均 16000/16000/0）。
- **影响面**: 现状无害（实测原子）；若未来 IDE/legacy 子进程并发写同一 ledger（多进程 O_APPEND 行级在本地 FS 基本安全，NFS 不保证），该锁给不出任何保护，属于误导性防御。
- **建议方向**: 模块级按路径缓存实例，或改用 `fcntl.flock`；至少删掉误导性锁并注释真实保障来源。

### T409 | spec R1 验收标准（"真实 pipeline 运行后 ledger 覆盖全部 dispatch"）无自动化护栏 | 测试缺口 | P2

- **证据**: `tests/` 中涉及 ledger 的仅 3 个文件（test_ledger.py、test_report.py、test_dispatch_helper_ledger.py），全部直接调 `_record_token_usage`/`TokenLedger`（unit 级）；无任何 run_chapter_step/genesis/closure → ledger 行数断言。spec 2026-08-14-cost-ledger-design.md R1 的验收句无对应测试。
- **根因**: dead-wire 两次复发（07-20、08-02 两次修复）期间 CI 均绿——回归不可见。
- **验证**: `grep -rln "render_report\|summarize\|TokenLedger" tests` → 仅 3 文件；用例清单见 test_ledger.py:12-160 / test_report.py:23-45。
- **影响面**: F301 修复后再次回归（新增调用点忘传/新门控）不会被 CI 拦截。
- **建议方向**: 集成测试以 fake OpenAI client 跑一个 genesis step + 一个 chapter step，断言 token-ledger.jsonl 行数 == dispatch 数（T401 方案下断言更稳定：不依赖 state 传参）。

### T410 | tenacity @retry 失败尝试的 token 消耗不计量：429/5xx 重试的已消耗 prompt usage 丢弃 | 计量缺口 | M

- **证据**: `_call_llm_streaming_with_retry`（:1454-1484）异常路径不返回 usage；仅成功尝试的 usage 经 :1583/:1639 落账。429/5xx 响应常已产生 prompt 侧计费。
- **根因**: usage 只在成功返回值中携带，失败尝试无旁路记录。
- **验证**: 读码（retry 装饰器 + usage 返回路径）。
- **影响面**: 高重试率场景（并行波 4 并发 + 速率限制）下实际账单 > ledger 记录，偏差无界。
- **建议方向**: retry before_sleep 钩子里无法拿到部分 usage（openai SDK 限制）；务实方案是在 APIException 携带 response headers（x-ratelimit 系）时记一条 `usage_status=failed_attempt` 的 sentinel 行。

## 3. F301 修复可行性判定（读码推导，未改码）

**结论：可行，但"逐调用点传 state"是高摩擦低收效路径；推荐 T401 的"记录点去 state 门控"路径。分级如下。**

| 层级 | 调用点 | 障碍 | 判定 |
|---|---|---|---|
| L1 一行改动 | genesis:321、closure:294、triggers:542、cli:140、cli:819（state 均在作用域） | 无序列化问题（同进程活对象）；唯一坑是 chapter 仍恒 0（E1） | **可行，5 处 × `state=state`** |
| L2 签名穿透 | audit_layer:170（run_audit_layer + 调用方 chapter_loop:2969）、revision_router:166（dispatch_escalation + 4 调用方：chapter_loop:647/1059、cli:298、genesis:245） | 机械改 6 文件；genesis escalation 调用点 state 可得 | **可行，约 6 处签名 + 5 处调用** |
| L3 架构冲突（不应传 state） | 并行审计波（parallel_dispatch:86 经 ReviewTask）、并行 post-draft（chapter_loop:2433/2440） | 代码自述不变式："Worker threads never touch PipelineState directly"（chapter_loop:2400-2401、state.py:513-514，single-writer/actor 模型）。传 state 会让 worker 并发执行 `rec["prompt_tokens"] += ...`（:1339-1342，无锁读-改-写）。E5(a) 实测 8×2000 并发 0 丢失（GIL 下窗口极小），但这是违反代码库自己的并发契约，而非被验证安全的操作 | **不推荐传 state**。替代：DispatchResult（dispatch_helper:340-346）加 usage 字段，主线程 merge 时落账；或直接走 T401（记录点自落账，state-free） |

## 5. 总结

1. **全链一句话**: 产生面唯一进程内 LLM 入口（_call_llm_streaming）计量代码完备，但落账面收窄为单调用点（dispatch_helper:1346）且被 state 双重门控——13 个 API 调用点仅 3 个通电（23%），IDE/legacy 子进程路由 0%（设计性），生产目录零 ledger（F1115 复认）；汇总面（summarize/render）功能正常却只有手动 CLI 一个消费者，报告面自身还有三处正确性缺陷（T404 未知模型 $0、T405 分数吞噬、T406 章维坍缩）。
2. **dead-wire 已两次复发**（07-20、08-02），每次修复都只接了一段；根因是落账 API 把 durable 写绑在 transient state 后面（T401）且无集成护栏（T409）。
3. **F301 修复判定**: 5 处一行 + 6 处签名穿透可行；2 处并行路径传 state 违反代码库自身 single-writer 契约（应改 DispatchResult 携带 usage 或记录点自落账）；子进程路由 state 不可穿越，需 --json/估记行/子进程直写三选一。推荐以 T401（记录点去 state 门控，chapter 用 :1520-1524 现场值）一次性接通 API 面，改动面比"全调用点传 state"小一个数量级。
4. 新增 findings 10 条：P1×2（T401 修复形状、T404 静默 $0）、P2×5（T402 消费端、T403 resume、T405 分数吞噬、T406 章维失义、T409 无护栏）、M×3（T407 mkdir 副作用、T408 假锁、T410 重试盲区）。
