## 2. pickle / 序列化边界

**无 pickle 面。** `src/`、`scripts/`、`tools/` 全量 grep：零 `multiprocessing` / `ProcessPoolExecutor` / `import pickle` / `fork()` / `spawn()` / `asyncio`。全部子进程边界（`phase_runner.py:87`、`scoring.py:304,343`、`dispatch_helper.py:1910` legacy `uv run shenbi-dispatch`、`dispatcher/modes/codex.py` codex agent）均为 **argv + stdout JSON 文本协议**，不传 Python 对象，不存在跨进程对象状态一致性问题。子进程继承的唯一状态是 `os.environ.copy()`（dispatch_helper.py:1904）——纯只读快照。结论：§5 通用维度 4 的 pickle 小项记"不适用"。

### T601 | 并行审计波 integrity findings 读改写竞态：同章并发审计互相覆盖 `.integrity-findings-NN.jsonl`，G4 检查面静默丢失 | 并发竞态 | P1

  ```
  round 0..4: expected_lines=2 actual_lines=1   (5/5)
  SUMMARY expected=10 actual=5 lost_rounds=5/5
  ```
  复现原理 = 真实控制流：主线程预持 `audits/` 目录 flock（safe_write 内部唯一的锁），两个 worker 线程先完成 `read_text`（读到同一旧内容）再阻塞在 flock 后的 replace 上——精确模拟并行波中两个同章审计 skill 的交错。
- **根因**：`src/shenbi/pipeline/dispatch_helper.py:1039-1054` —— `existing = out.read_text()` → 拼接 → `safe_write(out, existing)`。safe_write 的目录 flock 只串行化最终 replace（safe_write.py:103 在 replace 前才 `_acquire_lock`），**读发生在任何锁之前**，整个 RMW 事务无锁。truth_io.py:10-14 的文档明确指出这正是 spec §2.2 lost-update race 并为此提供 per-path 锁，但 `_append_integrity_findings` 没有走该模式。
- **验证**：并行波调用链实核：chapter_loop.py:2594/2618 `dispatch_reviews_parallel`（7 核心 + N genre 同章并发）→ worker `dispatch_skill` → `_write_parsed_outputs._write_one`（dispatch_helper.py:1163）→ `_append_integrity_findings`，写入键 `chapter-N` 由被审文件名决定（:1041-1043）——**同章所有并发审计共享同一 findings 文件**。
- **影响面**：两个并发审计同时产出完整性问题（prose 泄漏/fence 不平衡/审计完整性/行引用偏移——:1151-1163 的 6 类检查）时，后写者覆盖前写者，G4 checker 读取的 findings 缺失 → 有问题的章节可能漏检通过。属"静默错误审计结果"路径，但限于 integrity-findings 旁路账本（非主审计输出），故 P1 而非 P0。
- **建议方向**：迁移到 `truth_io._path_lock` 同款模块级 per-path `threading.Lock` 包住整个 read-merge-write；或直接复用 `write_truth_file(mode="append")` 语义。补一个并发压力测试（现 tests/unit/pipeline/test_truth_io.py 只测 truth_io 自身）。

### T602 | TokenLedger 锁是每实例新建的"装饰性锁"：`_record_token_usage` 每次 record 新建实例，锁零互斥；内存 `state.token_usage` 的 `+=` 绕过 PipelineState._lock | 保护失效（潜伏） | P2

  ```
  lock identity: l1._write_lock is l2._write_lock -> False

  ```
  8 线程 × 200 条全部落盘无损坏——但完整性只靠每条单次 O_APPEND 小写入的内核原子性，与锁无关（锁对象互不相同，从未互斥）。

### T603 | safe_write M5 回退分支 1s 后无条件夺取存活锁：O_EXCL lockfile 互斥可被破坏 | 边界缺陷 | P2

- **证据（实跑复现）**：`/tmp/t6x/r3_m5_stale_takeover.py`（进程内 monkeypatch `fcntl.flock`→OSError 以进入 M5 分支，仅测试进程内生效）：
  ```
  writer completed in 1.07s (backoff path ~1.0s + takeover)
  holder still inside its critical section: True
  REPRODUCED: M5 stale takeover broke mutual exclusion on a live lock
  ```
  持有者创建 lockfile 后存活 3s；写者在 ~1.07s 完成写入——此时持有者仍在临界区内，且写者已 unlink 并重建了对方的锁。
- **根因**：`src/shenbi/safe_write.py:75-91` —— 10×0.1s 退避后 `os.unlink(lockfile)` + O_EXCL 重建，无任何存活判定（无 PID/心跳/mtime 检查）。1s 退避不足以区分"崩溃残留"与"慢而活的持有者"（大文件 fsync、Windows/网络 FS 延迟轻松超 1s）。级联效应：写者 finally 的 unlink（:123）还会误删后续第三者的锁。
- **验证**：POSIX 上 `fcntl.flock` 实际总是可用（:54-62 的 ImportError/OSError 分支日常不可达），故主平台不触发；触发面 = Windows（flock 分支整体跳过）+ flock 失败的网络 FS。
- **影响面**：M5 生效平台上并发 safe_write 失去互斥——对全文件 replace 是最后写者赢（可容忍），对 RMW 调用方是丢更新。
- **建议方向**：lockfile 内写 PID+时间戳， takeover 前校验进程存活 + 锁龄下限（如 >30s）；或 takeover 改为 rename 抢占并检测被抢方写入的墓碑。

### T604 | 紧急清理无 one-shot latch：优雅关机时 `_emergency_cleanup` 确定性双执行（步骤边界一次 + atexit 一次） | 信号/atexit 交叠 | P2

- **证据（实跑复现）**：`/tmp/t6x/r4_atexit_double_cleanup.py` 用真实 `crash_recovery` 函数按真实关机序列驱动：
  ```
  after step-boundary: snapshot_calls=1
  after atexit:        snapshot_calls=2
  REPRODUCED: _emergency_cleanup executed 2x on one graceful shutdown
  ```
  （计数 wrapper 委托真实 `_snapshot_chapter_files`，计数即真实调用次数。）
- **根因**：`src/shenbi/pipeline/crash_recovery.py:78-89` 的 `_check_emergency_flag` 先清 `_emergency_flag` 再执行清理——该复位只防"步骤边界重入"，**防不了 atexit 路径**：`:66` `atexit.register(_emergency_cleanup)` 无条件注册，解释器退出时直接调用（:102-105 回退 `_emergency_state`），不看任何标志。双执行内容：二次 `save_state`（:126）、二次 emergency 快照同路径覆盖（:138）、二次 `clear_staging`（:147）。
- **验证（信号语义补充）**：`_handle_emergency_signal`（:69-75）只对**收到的那个信号**恢复 SIG_DFL——先 SIGINT 后 SIGTERM 时 SIGTERM 处理器仍会再执行一次（标志重置，幂等无害，记录为边界）。第二次同信号直接硬杀、atexit 不运行（Python 信号死亡不走 atexit），staging 得以幸存但状态不落盘——resume 语义可恢复，接受。
- **影响面**：与 F318 的交付面（atexit 清 staging 丢未 commit 输出）交叠，本条增量是**双执行机制本身**：若未来在 cleanup 中加入非幂等动作（如递增 retry 计数、追加关机事件到 trace），双执行立即放大为数据错误；当前动作幂等故仅 P2。
- **建议方向**：加模块级 `_cleanup_done: bool` latch（或 `functools.once` 语义），`_emergency_cleanup` 入口检查；`_check_emergency_flag` 与 atexit 共用。
